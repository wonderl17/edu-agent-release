# Codex runner: activation and recovery preparation

This is local development, not an installed Production capability. Do not push a new opted-in product version or activate the public release workflow until the remaining readiness items below are resolved. Actual installation/release requires the product repository's `edu-agent-deploy` workflow and explicit release authorization.

## Artifact and configuration boundaries

- Opted-in product source has `tools/codex-agent-runtime/release.json`. CNB schema 3 requires API, Worker, Web and Codex runner images at fixed digests; the exact protocol and installed SDK are verified in the image. Old schema 2 packages remain valid without a runner.
- `server/codex_runtime.py` is a root-owned, mode-0600 target helper at `/opt/teaching-ai-production/operations/release/codex_runtime.py`. The receiver, registry adapter, contract helper, configuration operator and patched startup policy are one installation set. The current host files have been retrieved read-only through the existing pinned SSH connection; the startup patch passes ten local policy checks against those exact bytes, including installation guards. The coordinated installer below holds both existing release and maintenance locks. This does not install the helpers or verify new files' target ownership. Recheck hashes immediately before any separately authorized installation.
- The root-only `server/codex_configure.py` operator tool belongs to the same reviewed installation set. It is not an additional remote SSH action and is not installed by the public release package.
- `/opt/teaching-ai-production/environments/codex-runtime.json` is root-owned mode 0600, has no symlink components and is at most 16 KiB. Exact fields: `schemaVersion: 1`, two distinct random `runnerToken`/`egressToken` strings (32–128 URL-safe characters), `modelBaseUrls` (1–8 exact HTTPS bases), `rolloutMode` (`closed` or `allowlist`) and `userIds` (at most 20 distinct IDs; required for `allowlist`). Initial admission is `closed`. Never put provider credentials into this file, a command line, a build or a report. Service tokens are generated and written locally within the restricted installation context.
- The runner is UID 1000, read-only, has all capabilities removed, no host or business volumes, no public ports and only the internal `teaching-production_codex-api` bridge. It is capped at 1 CPU, 768 MiB and 128 PIDs; only a 128 MiB `/tmp` tmpfs is writable. Planner concurrency is 1. These are configured limits, not verified capacity for a specific production workload.
- The existing API joins that private bridge with alias `codex-agent-egress`. Its model proxy binds only that private interface on 4987. It accepts exact approved Responses endpoints, checks all IPv4 DNS answers, pins the approved IP for TLS while verifying the original hostname, refuses redirects and bounds size/concurrency/time. The API retains its existing data connections; no additional service with external routing is introduced.

## Activation behavior implemented locally

1. The existing receiver verifies the complete package and images. It constructs the runtime addition from root settings, renders the full candidate Compose and passes the existing whole-configuration policy before stopping services, entering maintenance or migrating. A host missing compatible Codex helpers refuses with `CODEX_RUNTIME_ACTIVATION_NOT_INSTALLED`.
2. The receiver caches that accepted candidate. Under maintenance it stops API admission, drains existing jobs, stops Workers and runs the existing additive migration procedure. API and both Worker stops must preserve container/image identity and finish with exit code zero, without OOM or restart; a successful Docker stop command alone is insufficient. Incomplete shutdown restores the prior services before migration. No release-time backup is introduced.
3. Activation writes the accepted candidate, starts the runner and waits for its verified SDK health before starting API/Workers/Web. Data services and the gateway are preserved.
4. Postflight verifies the actual runtime image, private runner metadata, private API proxy protocol, unauthorized-request rejection, existing application checks and unchanged data/gateway identities. Health checks do not invoke a model. The normal host health snapshot includes the private endpoint probe as well, so a dead proxy is visible after deployment.
5. On failure or cancellation after activation, inspect the actual API/Workers, stop API admission, drain queued work with the candidate general Worker, and require clean Worker exits before restoring the exact previous override. The image must match the original or accepted candidate. If only the exact original, already drained business containers remain stopped, a runner-start failure can restore them directly. Missing/unexpected applications, an unavailable drain Worker or incomplete shutdown leave the candidate configuration in place and report `DEPLOY_FAILED_ROLLBACK_INCOMPLETE` with `rollbackCauseCode`; they do not recreate old Workers over unknown work. Returning to a three-image package removes only the uniquely owned, stateless runner container after the old applications start; a wrong project/service label, unexpected container identity or any non-tmpfs mount prevents removal. No volumes are removed.
6. Failure before activation restarts the original API/Worker container IDs. Both recovery paths wait up to 180 seconds for health and then verify the old version/SHA, image IDs and immutable data/gateway identities. Unhealthy recovery is `DEPLOY_FAILED_ROLLBACK_INCOMPLETE`, not success. Configuration recovery never claims to restore the database; migration attempts still require database review.

## Admission changes and token rotation implemented locally

Do not directly edit the active settings file. After authorized installation, the root operator can run the fixed `codex_configure.py` with `status`, `apply` or `recover`. `status` returns current settings/override SHA-256 hashes, rollout mode and account count; it never returns tokens or account IDs. `apply` reads a JSON request from stdin with exactly `settingsSha256`, `overrideSha256` and `settings`. Prepare this input in a root-only file, use the observed hashes and the complete next settings, and redirect it to stdin; no credential values belong in shell arguments or history. The configured model endpoints cannot change through this operation.

The tool acquires the existing release lock and maintenance lock, verifies the old state is healthy and rejects stale requests. It validates the new complete Compose against explicitly approved settings without modifying the live settings. A mode-0600, fsynced journal records both exact file versions before the API is stopped. It then replaces both files, recreates only the runner and API, and verifies their effective configuration, unchanged application version/images and all seven other service identities. Workers remain running; closing admission keeps workflow execution enabled so accepted tasks can finish.

On an ordinary failure it restores both previous files and verifies old health. If recovery fails or the process exits between file writes, the journal remains and ordinary deployment/stage/host-start operations refuse to proceed; monitoring reports `CODEX_CONFIGURATION_PENDING`. Run `recover` under the same root scope. An uncommitted journal restores the old pair. A durable committed journal finishes cleanup of the already verified new state, so a successfully closed account is not reopened merely because the process exited before returning its receipt. Recovery refuses file contents changed by another operator. Receipts contain hashes and fixed status codes; completed journal and candidate files are removed. This is recoverable coordinated replacement, not a claim that two filesystem renames form one atomic operation.

The procedure has real-file fault injection and actual Compose policy coverage. A separate local suite now exercises the transaction against the full linux/amd64 API image and real runner, PostgreSQL and Redis: admission changes, token rotation, API-start failure, interruption between writes and recovery after a committed revocation. Five other application services are inert identity fixtures. This does not prove a full-stack release or actual host installation.

## Coordinated initial host installation prepared locally

This section is an operator handoff, not authorization to execute it. The installer prepares host control support only; it never changes Compose, invokes a service restart, migrates a database, activates a runner or opens admission. It requires the original healthy eight-service application; it is not an updater for an already active Codex runtime.

Prepare a local bundle from the freshly audited source directory:

```sh
python3 scripts/prepare_codex_host_install.py --audit-dir <private-audit-directory> --output-dir <local-bundle-directory>
```

The audit must include `installation-precondition.json` (schema 1, exact Production host/root, nine paths, root/0600 metadata and SHA-256 hashes), plus the corresponding existing source files. No provider credentials or existing settings contents belong in the audit. The builder requires the exact original source hashes, applies the startup patch with zero fuzz, compiles the six code payloads, and emits `manifest.json`, `install.py` and `files/` beneath a directory named by the manifest's SHA-256. No credentials are generated at preparation time. Previously generated bundles become obsolete when installer or payload source changes; retain them only as historical evidence.

Before a separately authorized installation, recheck current source hashes and in-flight operations. Copy the reviewed bundle as root to the fixed directory `/opt/teaching-ai-production/operations/release/host-install-bundles/<manifest-sha256>/`, with directories 0700 and all eight files 0600, owned by root:root and without links. The operator then invokes `/usr/bin/python3` on that exact directory's `install.py` with `check`, `apply` or `recover`; no alternate target path is accepted. `check` compares current files and dependencies with the manifest and checks application health without writing tokens, locks, bytecode or state. A stale baseline requires a fresh audit and reviewed bundle; do not edit hashes to bypass it.

`apply` accepts exactly `{"modelBaseUrls":["https://approved-provider.example/v1"]}` from stdin. Replace the example with the explicitly approved endpoint; do not inherit a provider from the operator shell or include a provider API key. Initial service tokens are generated locally, are distinct, and remain in root-only settings/journal files. Initial mode is always `closed` with an empty account list. If previously audited settings exist, only the same endpoints and already closed settings are accepted, and the exact old bytes are retained.

The installer acquires both nonblocking control locks, revalidates the baseline, records application config hash/container IDs/images/start times, and fsyncs a recovery journal before replacing anything. It first replaces both control entrypoints with refusal stubs and waits for previously loaded control processes to exit; it does not kill them. Only after that fence does it replace the four helpers and settings, followed by the final startup/receiver code. The new entrypoints and configuration tool reject control actions while the journal remains. A crash before both stubs are present leaves original helpers untouched; a crash while restoring original entrypoints occurs only after all original helpers/settings have been restored. This is coordinated, recoverable replacement, not an atomic multi-file rename.

Before committing it verifies every installed byte, unchanged dependencies, application config and service identities/start times. Ordinary precommit failure attempts restoration. An interrupted or incomplete transaction retains `codex-host-install.pending.json`; repeat `recover` from the exact same reviewed bundle. Uncommitted state restores all original files, including removal of originally absent files; a durable commit preserves the verified installed state. Recovery refuses unknown external file changes, changed application config or replaced containers. It may acknowledge an external restart of the same container/image and reports it explicitly. Receipts contain hashes and status only. Do not remove the journal or override a refusal manually. An abrupt OS failure during the temporary-file write may leave a restricted `.install-*` sibling; it is not a live target or used by recovery, and cleanup requires checking ownership and transaction history.

Readiness evidence is local: 18 real-file tests include all 13 apply and 13 restore boundaries, failures, stale inputs, external edits, permissions and locks. `verify_codex_host_install.py` additionally runs the exact bundle and archived host bytes as root in a read-only, networkless Linux container, with fresh tmpfs target/locks and no Docker socket. Six checks cover readonly preflight, real `/proc` fencing, closed settings/root permissions, actual Linux lock contention and 39 actual process exits across apply/recovery boundaries. The application health snapshot in this installation suite is synthetic; complete application behavior has separate evidence. No target host installation is claimed.

## Local evidence and reproduction

Run from `scripts/`:

```sh
python3 -m unittest test_codex_host_install test_codex_configuration test_codex_activation test_codex_runtime test_cnb_runtime test_cnb_release test_cnb_build test_tencent_production_stage test_tencent_production_resume
```

`scripts/verify_codex_host_policy.py --ops-source <local-base-copy> --output <local-report>` applies the CNB/Codex patches to a temporary copy with zero patch fuzz, exercises actual Compose rendering and synthetic host failures, and records hashes. It never installs the patch or executes host service commands. Local non-root fixture checks do not prove Production ownership or permissions.

`scripts/verify_codex_isolation.py --image <local-runtime-tag> --api-source <product-agent.egress.ts> --output <local-report>` requires a local Unix Docker context. It creates only a uniquely named synthetic project, checks raw TCP isolation, private API binding, DNS refusal and the real release health probe, then repeats after restart and removes its own containers/networks. It uses the real compiled proxy module, not the full API application. The prior separate-egress-container raw TCP failure remains in the product's private evidence directory; the replacement topology removes that extra routed service and retains the negative checks.

`scripts/verify_codex_application.py --api-image teaching-codex-api:<local-tag> --runner-image teaching-codex-runtime:<local-tag> --output <local-report>` uses the full API image's original entrypoint, real runner and fresh local PostgreSQL/Redis. Both application networks are internal, no ports are published and no model credentials are supplied. The actual HTTP API checks closed/default admission, an explicit account allowlist, administrator non-bypass, ownership, historical access and durable cancellation after API restart. The real configuration transaction recreates containers and checks unchanged images and seven unrelated container identities across rotation, failure and interrupted recovery. Production project names remain fixed in the implementation; the verification process adapts its module constants to a randomly named local project. Local image IDs replace registry references only in this harness. The report records these limitations and cleanup; it does not claim production migration, old package recovery, in-flight generation drain or actual root host permissions.

`scripts/verify_codex_shutdown.py --api-image teaching-codex-api:<local-tag> --runner-image teaching-codex-runtime:<local-tag> --output <local-report>` exercises full-API SIGTERM with a deterministic planning HTTP fixture, real database outage, durable lease expiry and restart of the same operation. This is separate from provider/SDK inference and the configuration suite.

`scripts/verify_codex_workers.py --api-image teaching-codex-api:<local-tag> --runner-image teaching-codex-runtime:<local-tag> --worker-image teaching-codex-worker:<local-tag> --output <local-report>` runs both original Worker entrypoints with fresh PostgreSQL/Redis and a local model HTTP fixture on an internal network. It checks in-flight homework-proposal/legacy-slide saves, immediate stop of consumption, queued work after restart, a real 40-second incomplete drain, receiver stop rejection, and same-Job recovery after real BullMQ lock expiry. It records image/source hashes and removes its own test resources. These cases do not cover initial full-lesson/full-deck generation, all domain Jobs, actual package activation or production data migrations.

`scripts/verify_codex_package_recovery.py` accepts local candidate API/Worker/runner tags, `--old-image-proof`, `--queue-probe` and an existing output directory via `--output`. It reinspects all three deployed immutable amd64 image identities. In a new internal Docker project it applies the old image's complete Prisma migration history, starts its original API/Workers/Web, applies the candidate migrations, starts the candidate API/Workers/runner, and exercises the receiver's real rollback drain while a synthetic proposal is generating. It then restores the original API/Worker/Web images and proves the old client and Worker can still read/write the migrated database while the new proposal remains saved. PostgreSQL and Redis identities/start times are preserved. Model HTTP is deterministic and has no provider credentials. This is a scoped compatibility and drain proof, not a complete release: candidate Web, object storage, public TLS, root installation, signed packaging/version policy and the complete receiver transfer/activation sequence remain outside it.

`scripts/verify_codex_release_lifecycle.py` adds the real eight-service baseline (API, both Workers, Nginx Web, Caddy gateway, MinIO, PostgreSQL and Redis), the actual candidate Web build, and the Codex runner. The receiver's Web extraction checks, candidate preflight, queue drain, clean stops, Prisma migration, activation, postflight, failed-activation rollback and explicit original-package resume execute against those containers. A control container performs probes; all networks are internal and no ports or provider credentials are supplied. Signed upload/read and anonymous denial preserve a synthetic object across both upgrade and rollback. The actual API route through the gateway verifies default-closed admission, including for an administrator.

This local lifecycle suite uses historical version `0.0.131` and the existing explicit same-version source-change contract; a separate negative check confirms that candidate `0.0.131` is refused against current Production `0.0.132`. It never changes release version policy. The candidate uses an all-zero synthetic source SHA, local image IDs, local ownership/path adapters and a gateway-internal equivalent of the host-loopback HTTP check. Registry transport is replaced with already inspected images; no signed CNB package, public TLS, root installation, production data or production resource-capacity claim follows from this suite. The receiver's `PROJECT` constant remains `teaching-production` by default and is changed only inside the local verification process, just like the existing runtime/configuration verifiers; it is not an environment or request setting.
