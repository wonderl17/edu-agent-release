# edu-agent releases

Public orchestration for `shukezhinao/edu-agent` and `wonderl17/edu-agent`.
Application code, private build scripts and signing material stay outside this repository. Verified desktop installers are also available as public GitHub Release assets.

## Run a release

Cloud Production uses **Actions → Tencent Production**, with one fixed Tencent host and the canonical `shukezhinao/edu-agent` source. Only full commits in canonical `main` history are accepted. The workflow validates canonical source and delegates all Web/API/Worker image builds to the private CNB project `shukezhinao/edu-agent-cloud-build`; partial targets are unsupported and must not be silently widened. Production Web uses `/api` and the baked `shukezhinao-prod` environment label.

- `verify` checks an already healthy target, trusted source, and private CNB repository/history access without building or deploying. It detects expired controller credentials, but does not prove build-write permission or registry pulls; use a confirmed `stage` when a fresh build/delivery check is needed.
- `stage` requires an exact `source_sha` and explicit confirmation. It builds in CNB, pulls immutable image digests on the target and validates the actual Web bytes. The receiver may load images and unpack static files, but never touches services, queues or databases, and never records a Cloud version attempt. The registry path requires an active Production target; legacy COS staging retains the original initial-cutover gate.
- `deploy` builds and activates the complete package on a healthy Production target. An already running source/version is skipped by default. For an explicitly requested full cache comparison, set `rebuild_current=true` with the exact current `source_sha` and `confirm_release=yes`; it rejects a different source/version and repeats the normal build, package, migration and runtime checks. Automatic releases and `resume` cannot enable this option.
- `resume` requires the exact source and prior stage/release `previous_transfer_ticket`. It reuses the original registry manifest and image digests (or copies a legacy COS object), skips rebuilding, and repeats identity, migration and runtime verification. Releases do not create pre-release backups; the Mac daily recovery policy remains independent. Initial cutover activation requires a separate root-controlled data-import gate. Only manual exact-source original-package resume may use that gate, binding its ID through the new transfer ticket and deployment and matching the precise package hash/size. It skips the ordinary server attempt record because no current Web exists; GitHub still records the Cloud attempt and the one-shot gate records activation state. Bootstrap readiness is never health evidence.

Mutating operations require `confirm_release=yes`, `RELEASES_ENABLED=true` and `TENCENT_PRODUCTION_ENABLED=true`. The workflow reuses `production-release` for existing source App authentication, requesting only a canonical-repository read token, and adds dedicated Production SSH/host-pin fields. Existing GCP and Desktop secrets are not passed to this job. No GCP identity, Desktop signing material or long-lived cloud storage key enters this job. Target/project, protocol, image namespace and COS relay destination are fixed in code. No local build fallback is used.

Production acceptance must match the Web version and full private source SHA and check the actual API and both worker images. Preserve both `https://shukezhinao.321weiqi.com` and `teaching-ai-agent://app` in the private storage CORS allowlist during releases and restores. Verify PUT preflight, signed upload and readback separately for each origin; a successful website upload does not establish Desktop upload support. Keep the bucket private and use exact allowed origins without a wildcard. Runtime receipts and business data remain private.

**Actions → Release** now accepts only `desktop` and Desktop `resume`, preserving macOS/Windows signing and original COS/R2/private GitHub Release destinations, plus verified public installer copies. Both private source repositories remain available for these Desktop operations. Desktop packaging uses isolated target workspaces, with concurrency 2 by default; environment variable `DESKTOP_PACK_CONCURRENCY` in `production-release` accepts 1–3 (1 serializes the targets). Common Web/sidecar builds run once. Old `verify`, `cloud` and `migration-bootstrap` inputs cannot enter this workflow, and its GCP authentication/setup steps are removed. Retired private Cloud/Legacy workflows remain disabled. The former GCP controller code is retained only as historical implementation, not a current entry point.

Every 15 minutes, **Check source versions** checks canonical `main`. Root-version growth dispatches only `tencent-production.yml`; Desktop-version growth still dispatches `release.yml`. Cloud automatic publication additionally requires `TENCENT_PRODUCTION_AUTOMATIC_ENABLED=true`; it is enabled for normal Production operation. Close it before pushing a new Cloud version when an explicit stage/acceptance/resume window is required, and re-enable it after successful activation without changing Desktop. Cloud starts above baseline `0.0.125`; Desktop retains baseline `0.0.121`. Attempt metadata prevents repeating failed or already queued versions. Stage metadata uses a separate task and cannot advance the Cloud cursor. Explicit recovery is required after a failed attempt.

**Check source versions** is scheduled every 15 minutes, but GitHub may delay scheduled runs. Its manual `dry_run=true` default checks source access and version eligibility without dispatching, advancing attempt cursors, or updating the scheduler activity file. Use `dry_run=false` to request an immediate normal poll; only eligible unattempted versions are queued. This is not a retry for a failed version.

During cutover, cancel any old queued/running Cloud attempts before freezing the source. A merged workflow does not rewrite an already running historical revision. Do not re-enable old GCP workflows or modify Desktop/CLIProxyAPI as part of this Cloud move.

GitHub [disables public scheduled workflows after 60 days without repository activity](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). After a successful poll, the scheduler uses this public repository's `GITHUB_TOKEN` to initialize `config/scheduler-activity.json` with the current UTC date, then updates that date through a normal maintenance commit only after at least 30 days. Future dates are preserved. This file contains only the maintenance date; no private source or secrets are committed. The check runs in this public repository on a standard runner and does not use private-repository minutes.

Cloud uses `TENCENT_BUILD_BACKEND=cnb` after the CNB stage acceptance check. GitHub remains the source validator/orchestrator: it copies only the selected committed tree under `source/` in the private CNB repository, records both canonical SHA/tree and CNB snapshot SHA, then invokes the exact snapshot through `api_trigger_tencent`. It never mirrors the canonical Git history or passes GitHub/Production credentials into CNB. The pipeline uses 8 amd64 CPUs and the CNB-provided rootless Docker service, with registry build caches for each component. Only CNB's temporary job token pushes images and writes the completion annotation.

For older source without `tools/codex-agent-runtime/release.json`, if `tools/codex-agent-runtime/Dockerfile` exists, the builder also warms `cache-codex-runtime:main` after verifying the three release images. This is a cache-only build of that isolated context, bounded to five minutes, with `mode=max` registry caching. Benchmark builds import main but only export their own benchmark tag. Missing older source directories are skipped; cache build/export failures or timeouts do not block the release, while cancellation still stops the build process group. No fourth image is added to the release manifest and no runner service is deployed. Future authorized runner image builds can import this cache. Registry caches preserve installed dependency layers, not npm cache mounts; mounts help local rebuilds, while a changed lockfile on a fresh CNB builder may still download dependencies. The private log records the cache build outcome and elapsed time; completion alone does not prove a cache hit or successful export. Total build timing and CNB billing include this step; original-package resume does not run it.

The controller checks the private repository's visibility, source tree, request ID, snapshot SHA and exact digest-pinned image set. Schema 2 retains the three original images. Opted-in source uses schema 3 with a required `codex-runtime` fourth image and a protocol/SDK contract. The root receiver pulls only `docker.cnb.cool/shukezhinao/edu-agent-cloud-build/{api,worker,web,codex-runtime}@sha256:...`, checks config IDs, platform, source/version labels and actual Web metadata, and retains the original manifest for `resume`. On the current Docker containerd image store, which exposes manifest IDs, it hashes the local manifest and config bytes through the fixed `/run/containerd/containerd.sock` `moby` content store and checks their chain and root filesystem identity. Stage does not activate containers or alter services, databases or queues. CNB cancellation is propagated before the existing SSH cancellation path. Build and pull timings are saved in private receipts.

**Four-image runner packaging is implemented and locally verified; its target helpers are not installed on Production.** The explicit `tools/codex-agent-runtime/release.json` source contract binds a supported protocol and an exact SDK version to both package manifests. The controller reads it from the selected Git tree, not the working directory, and refuses a green build that silently omits the required image or changes its SDK contract. CNB builds the isolated context with the existing scoped cache, source/version/protocol/SDK labels, and requires its success before publishing the manifest. Both builder and receiver use `docker create/cp` to read the actual installed SDK and release metadata without starting the candidate; the receiver also checks its non-root user and entrypoint. `resume` retains all four digests and the same protocol/SDK metadata. New COS builds reject opted-in source before the production executor records an attempt or builds; an automatic poll may already have recorded its dispatch attempt and retains that cursor. Old schema-2 and legacy COS original-package recovery remain supported.

The local receiver now supports schema-3 candidate validation, runner-first activation, private endpoint health and old-package recovery. A host missing the compatible policy helpers still refuses activation with `CODEX_RUNTIME_ACTIVATION_NOT_INSTALLED` before maintenance or migration. Both pre-activation restart and post-activation rollback require verified old health, version and image identities; database restoration is never inferred. This code is not installed on Production. Do not enable publication of opted-in source until the remaining readiness checks in [the runtime handoff](server/codex-runtime.md) are complete.

The target policy is `server/codex_runtime.py` with `server/production-ops-codex.patch` (not installed). The runner has only one internal network and forwards through a private listener in the existing API. The previous separate externally routed proxy was removed after its raw TCP database-access negative test failed; that evidence is retained. The replacement passes local direct-IP isolation, private-interface, DNS and release-health probes, including after restart, without privileged helpers or host firewall changes. Host patch tests use a local archived source copy, real Compose rendering and synthetic host state; a separate local full-stack suite covers activation and recovery. Neither proves installation or activation on the current Production host. The root-only `codex_configure.py` coordinates admission/token settings and override changes with a durable recovery journal, compares effective API configuration and preserves all unrelated services. Fault injection covers partial writes, failed restarts, committed-state recovery and conflicting operator edits.

`production-release` needs `TENCENT_CNB_TOKEN`, scoped to this CNB repository: code read/write, build trigger read/write, history and basic-info read. Production's root-only `operations/release/registry-auth/config.json` contains a separate registry-package read-only token. Both initial tokens expire on 2027-01-23 and need rotation before expiry. Source, cache layers and build logs remain private. `server/tencent_receiver.py`, `scripts/tencent_registry.py` and `scripts/cnb_release.py` are the versioned receiver sources; install together with root ownership and mode 0600 after checksum/lock checks. No cloud resources or deployment permissions are given to CNB.

Apply `server/production-ops-cnb.patch` to the existing root-owned `operations/startup/production-ops.py` under the same checksum/lock checks. It permits only this repository's exact API/Worker SHA-256 references alongside legacy local tags; arbitrary registries, mutable CNB tags and other Compose changes remain rejected. The receiver validates the complete candidate Compose configuration with that runtime policy before entering maintenance, stopping services or running migrations.

COS is retained only for explicit legacy package recovery/compatibility. Its upload endpoint remains ordinary Beijing, with `accelerated_upload=false`; CNB failure never falls back to COS, local building or GCP. Desktop retains its existing publishing destinations.

## Retired Tencent validation

The `teaching-validation` stack is stopped and retained. Its workflow has no schedule, a fixed false job guard, and is disabled in GitHub; both validation enable variables are false. Keep its historical implementation only for explicitly scoped recovery research. All normal Cloud releases and checks use **Tencent Production**. Never reactivate validation consumers alongside Production or run the old COS/backup deployment path as a fallback.

## Per-release CNB CPU usage

Every Tencent Production run writes a `CNB 发布额度` Actions job summary and a bounded `CNB release usage:` log line, including failures and cancellation when cleanup can run. The controller sums the CNB status API's `metricCoreHours` across all terminal pipelines; `metricDuration` is billing time in milliseconds, not controller elapsed/queue/deployment time. If core-hours are absent but billing duration and CPU labels are available, the result is explicitly estimated. Missing, partial or invalid metrics are pending, never zero. Accounting errors cannot alter the release result. After cancellation, stopping the build comes first; at most one 10-second read-only refresh reconciles its metrics. A hard-killed job or uncertain trigger can require later reconciliation.

The private CNB build title includes the public GitHub run ID and attempt, so the same attempt can be located later without exposing private build IDs in public logs. Each rebuild is a separate charge; `stage` owns the build usage and original-package `resume` adds zero CNB build usage. Desktop uses GitHub runners and reports zero CNB usage. The 160-core-hour percentage is a community-plan comparison, not the organization's remaining monthly balance or an invoice; object/Git storage are outside this CPU metric. No organization billing permission or new secret is required. See the [official CNB API schema](https://api.cnb.cool/swagger.json) and [pricing rules](https://docs.cnb.cool/zh/saas/pricing.html).

## Privacy and credentials

- A dedicated GitHub App is installed only on the two private source repositories. Read tokens fetch source; write tokens are issued only for private GitHub Release operations and expire automatically.
- Only the public controller is checked out by an Actions checkout step. Private source is fetched into a temporary directory and verified against its origin and trusted main history.
- Private stdout/stderr, exception messages and GitHub file commands never enter public logs, including failed commands. Public logs show fixed phases and status codes. Private temporary logs and source are removed after each run. Diagnose current Cloud failures in the target’s root-only release receipts/logs; public logs intentionally contain no build details.
- Desktop subprocess checkpoints add only fixed stage IDs, `start`/`success`/`failure` states, fixed platform labels and bounded elapsed milliseconds after private execution. The trusted controller validates the latest 256 records from a 16 KiB private temporary channel, then removes it. Nested and parallel timings overlap; the Actions job duration is the total. Arguments, paths, environment values, child output and exception text are never included; diagnostic I/O failures do not change the release result. Product source and package metadata are unchanged.
- No Actions artifacts or Actions caches are uploaded. The private desktop entrypoint can reuse an authenticated, encrypted dependency-only R2 cache; private source, signing state and product outputs are excluded. Missing or invalid caches do not block the build. Existing COS, R2 and private GitHub Release uploads continue. Only `ShukeZhinao-<version>-mac-arm64.pkg`, `-mac-x64.pkg` and `-win-x64.exe` are copied from the selected private Release to this repository’s public Release; size and SHA-256 must match before and after upload. A fresh build first copies matching local installer bytes and downloads only missing/mismatched installers; `resume` continues to download the original private Release assets. Source archives, logs, source maps, update packages and private release notes are excluded. Identical assets are reused; different bytes under the same name are rejected. Public tags target the controller commit, never the private source commit. The public write token stays outside private execution. A failed private publication remains failed even if its saved installers can be copied; cancellation stops the copy.
- Current Cloud workflows do not authenticate to GCP. Retired GCP resources and backups remain recovery material; restarting them requires explicit rollback authorization.
- The existing `production-release` environment is restricted to `main`; each workflow explicitly passes only its own credentials. No PR-triggered privileged workflow exists. Official setup actions are pinned to immutable commits.

Changing trusted source code or this controller can change what it publishes. Keep repository write access limited and review workflow/script changes as production access changes.

## Checks

`python3 -m unittest discover -s scripts -p 'test_*.py' -v`

Tests include success/failure output sentinels, injected Actions commands, cancellation cleanup, trusted-source checks and scheduler de-duplication. `Tencent Production / verify` requires live target health and checks source and CNB read access without building or deploying a product. `Check source versions / dry_run=true` checks the actual scheduler credentials and both version cursors without publication. Actual product publication is a separate explicitly confirmed operation.
